= Optimized connector для PostgreSQL
:toc:
:toclevels: 3
:sectanchors:
:source-highlighter: highlight.js

== Обзор

Параметры сравниваются с Debezium PostgreSQL `3.6.0.Final`.

== Как работает коннектор

Коннектор читает PostgreSQL через `pgoutput`, выполняет обработку собственным параллельным pipeline и работает как одна Kafka Connect task. Увеличение `tasks.max` не заменяет настройку внутренних потоков. Полная взаимозаменяемость всех конфигураций Debezium для этой версии не заявляется: ниже перечислены ограничения native path.

== Подготовка PostgreSQL

Требуются Java 21, Kafka Connect совместимой версии 4.3.x и PostgreSQL с `wal_level=logical`. Пользователю PostgreSQL нужны LOGIN, REPLICATION, доступ к базе, USAGE на схемы и SELECT на захватываемые таблицы. Права на создание publication нужны только при её автоматическом создании. Подготовку publication и replica identity согласуйте с администратором БД.

== Развёртывание

Соберите каталог плагина по инструкции в link:../../../../../optimized-connector-postgres/README.md[README модуля].
В каталоге должны находиться `optimized-postgres-connector.jar` и `postgresql-42.7.11.jar`.

Поместите каталог под `plugin.path` каждого worker и перезапустите Kafka Connect. Через `GET /connector-plugins` проверьте, что worker видит класс `io.cdcbench.connect.optimized.OptimizedPostgresConnector`.
Kafka Connect API и Kafka clients предоставляет worker. Пользовательские converters и SMT устанавливайте с их зависимостями.

== Минимальная явная конфигурация

Пример предназначен для нового, отдельно подготовленного slot и publication. `initial` читает существующие данные перед streaming; `no_data` не выполняет начальную выгрузку строк. Не подключайте оригинальный и наш коннекторы одновременно к одному slot.

[source,json]
----
{
  "name": "optimized-postgres",
  "config": {
    "connector.class": "io.cdcbench.connect.optimized.OptimizedPostgresConnector",
    "tasks.max": "1",
    "database.hostname": "postgres.example.com",
    "database.port": "5432",
    "database.user": "cdc_user",
    "database.password": "REPLACE_WITH_SECRET",
    "database.dbname": "application",
    "database.sslmode": "verify-full",
    "database.sslrootcert": "/etc/kafka-connect/secrets/postgres-ca.crt",
    "topic.prefix": "application",
    "plugin.name": "pgoutput",
    "slot.name": "optimized_application",
    "publication.name": "optimized_application_pub",
    "publication.autocreate.mode": "disabled",
    "table.include.list": "public\\.orders",
    "snapshot.mode": "initial",
    "schema.refresh.mode": "columns_diff_exclude_unchanged_toast",
    "include.schema.changes": "false",
    "extended.headers.enabled": "false",
    "tombstones.on.delete": "true",
    "heartbeat.interval.ms": "1000",
    "poll.interval.ms": "100",
    "max.batch.size": "8192",
    "max.queue.size": "32768",
    "optimized.execution.mode": "fast",
    "optimized.processing.workers": "1",
    "optimized.processing.chunk.size": "512",
    "optimized.max.inflight.transactions": "16",
    "optimized.max.inflight.bytes": "67108864",
    "optimized.transaction.spill.directory": "/var/lib/kafka-connect/optimized-spill",
    "key.converter": "io.cdcbench.connect.optimized.OptimizedJsonConverter",
    "value.converter": "io.cdcbench.connect.optimized.OptimizedJsonConverter",
    "key.converter.schemas.enable": "false",
    "value.converter.schemas.enable": "false"
  }
}
----

Замените адрес, имена объектов и секрет перед отправкой через `POST /connectors`. Пароли не сохраняйте в Git. Сертификат и каталог spill должны быть доступны на всех workers, где может запуститься task. `verify-full` требует сертификат с корректным именем сервера. Значения примера — выбранный профиль, а не новые defaults; например, tombstone явно включён для совместимости с потребителями compacted topics.

== Настройка коннектора

Во втором столбце приведены defaults оригинального Debezium 3.6 из сохранённого контракта, в третьем — фактические значения по умолчанию оптимизированного коннектора или необходимые явные значения. «Не задано» означает отсутствие настроенного значения, а не отключение всей функции. Значения `optimized.*` отсутствуют у оригинала.

REST `config()` нашего коннектора публикует сохранённый контракт оригинала. Его отображаемые defaults не всегда совпадают с runtime defaults `CandidateConfig` и `OptimizedSettings`. Поэтому важные параметры задавайте явно, как в примере. Поддерживаемые варианты приведены в таблице.

Heartbeat публикуется через task poll, а не независимым таймером доставки. Интервал не является гарантией появления события каждую миллисекунду указанного периода: snapshot, очередь и незавершённые batches могут задерживать отправку. Heartbeat event и `status.update.interval.ms` — разные механизмы. По умолчанию topic — `__debezium-heartbeat.<topic.prefix>`.

=== Производительность и память

[cols="40%a,25%a,35%a",options="header"]
|===
|Параметр и для чего он нужен | Оригинальный Debezium | Наш коннектор
|`poll.interval.ms` — интервал SourceTask poll | `500` | `100`; не меньше `1`
|`max.batch.size` — максимум records одного poll | `2048` | `8192`; положительное, не больше `max.queue.size`

|`optimized.processing.chunk.size` — размер порции внутренней обработки | Отсутствует | `512`, положительное целое
|`optimized.max.inflight.transactions` — число транзакций в обработке | Отсутствует | `16`, положительное целое
|`optimized.max.inflight.bytes` — порог памяти буферизации транзакций | Отсутствует | `67108864` байт, положительное; это не лимит heap всего worker
|`optimized.transaction.spill.directory` — диск для больших транзакций | Отсутствует | `${java.io.tmpdir}/optimized-postgres-transactions`; явно задайте рабочий каталог с контролем свободного места

`max.batch.size` задаёт предел выдачи одного poll. `optimized.processing.chunk.size` задаёт размер порции внутренней обработки.

Начните с явных defaults и измерьте throughput, p95, CPU, память, lag и размер spill. Затем меняйте только один параметр за прогон. Сравнение с оригиналом проводите при одинаковых Kafka Connect/JVM, данных, формате событий, snapshot, heartbeat и tombstones. Большее число потоков само по себе не гарантирует прирост.

== Ограничения и безопасное обновление

Неперечисленные параметры оригинала не следует переносить автоматически: `FastPathSelector` отклоняет настройки вне своего allowlist. В частности, в оптимизированном коннекторе нельзя задавать `max.queue.size.in.bytes`, `snapshot.max.threads`, `snapshot.fetch.size`, `snapshot.delay.ms`, `snapshot.isolation.mode`, `message.key.columns`, `slot.max.retries`, `slot.retry.delay.ms`, `lsn.flush.*`, `notification.*`, `openlineage.*`, `post.processors`, `publish.via.partition.root`, `replica.identity.autoset.values`. Наличие таких параметров в REST contract не означает их поддержку runtime.

Для `slot.stream.params` допустим `proto_version=1..4`; по умолчанию используется `1`, а при `two_phase=true` без явной версии — `3`. `two_phase=true` требует версии не ниже `3`; `streaming=on` требует явно указанной версии не ниже `2`. `streaming` принимает только `on`/`off`. `publication_names` нельзя задавать здесь: используется `publication.name`. Duplicate keys запрещены. Для two-phase, failover и distributed exactly-once проверьте поддержку выбранной конфигурации на своём стенде.

Логические сообщения по умолчанию выключены в native path. Для их включения задайте один из regex-фильтров `message.prefix.include.list` или `message.prefix.exclude.list`; одновременно оба запрещены. Тестируйте формат и фильтрацию до production.

`transaction.boundary` принимает `poll` или `connector`. Значение по умолчанию — `poll`. Для exactly-once настройте distributed worker и Kafka broker и проверьте выбранный режим транзакций.

Перед обновлением сохраните конфигурацию, текущий архив и offsets согласно xref:../upgrading.adoc[инструкции по обновлению]. Остановите захват без удаления slot, обновите plugin одинаково на всех workers и проверьте возобновление, lag и контрольные события insert/update/delete. Не меняйте одновременно topic prefix, slot, converters и семантику payload. Rollback должен сохранять позицию CDC; повторный snapshot вместо восстановления offsets не является доказанным rollback.

Связанные документы: xref:../operations.adoc[эксплуатация], xref:../upgrading.adoc[обновление и rollback].
