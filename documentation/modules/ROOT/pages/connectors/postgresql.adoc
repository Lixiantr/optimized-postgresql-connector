== Overview

This guide compares connector settings with Debezium PostgreSQL `3.6.0.Final`.

== How the connector works

The connector reads PostgreSQL changes through `pgoutput` and processes them through a native parallel pipeline within one Kafka Connect task.
Set the number of internal workers with `optimized.processing.workers` and keep `tasks.max` at `1`.
See the configuration reference for supported settings and native pipeline limitations.

== Preparing PostgreSQL

Use Java 21, Kafka Connect 4.3.x, and PostgreSQL with `wal_level=logical`.
The PostgreSQL user needs `LOGIN`, `REPLICATION`, access to the database, `USAGE` on the schemas, and `SELECT` on the captured tables.
Grant publication creation privileges if the connector creates the publication automatically.
Coordinate publication setup and replica identity with the database administrator.

== Deploying the connector

Prepare the plugin directory as described in the link:../../../../../optimized-connector-postgres/README.md[module README].
Include `optimized-postgres-connector.jar` and `postgresql-42.7.11.jar`.

Place the directory under `plugin.path` on each worker and restart Kafka Connect.
Call `GET /connector-plugins` to confirm that the worker can discover `io.cdcbench.connect.optimized.OptimizedPostgresConnector`.
The worker provides the Kafka Connect API and Kafka client libraries. Install custom converters and SMTs with their dependencies.

== Configuration example

Use this example with a new, separately prepared slot and publication.
`initial` reads existing rows before streaming. `no_data` begins streaming without an initial row snapshot.
Give each active connector its own replication slot.

[source,json]
----
{
  "name": "optimized-postgres",
  "config": {
    "connector.class": "io.cdcbench.connect.optimized.OptimizedPostgresConnector",
    "tasks.max": "1",
    "database.hostname": "postgres.example.com",
    "database.port": "5432",
    "database.user": "cdc_user",
    "database.password": "REPLACE_WITH_SECRET",
    "database.dbname": "application",
    "database.sslmode": "verify-full",
    "database.sslrootcert": "/etc/kafka-connect/secrets/postgres-ca.crt",
    "topic.prefix": "application",
    "plugin.name": "pgoutput",
    "slot.name": "optimized_application",
    "publication.name": "optimized_application_pub",
    "publication.autocreate.mode": "disabled",
    "table.include.list": "public\\.orders",
    "snapshot.mode": "initial",
    "schema.refresh.mode": "columns_diff_exclude_unchanged_toast",
    "include.schema.changes": "false",
    "extended.headers.enabled": "false",
    "tombstones.on.delete": "true",
    "heartbeat.interval.ms": "1000",
    "poll.interval.ms": "100",
    "max.batch.size": "8192",
    "max.queue.size": "32768",
    "optimized.execution.mode": "fast",
    "optimized.processing.workers": "1",
    "optimized.processing.chunk.size": "512",
    "optimized.max.inflight.transactions": "16",
    "optimized.max.inflight.bytes": "67108864",
    "optimized.transaction.spill.directory": "/var/lib/kafka-connect/optimized-spill",
    "key.converter": "io.cdcbench.connect.optimized.OptimizedJsonConverter",
    "value.converter": "io.cdcbench.connect.optimized.OptimizedJsonConverter",
    "key.converter.schemas.enable": "false",
    "value.converter.schemas.enable": "false"
  }
}
----

Replace the host, object names, and secret before calling `POST /connectors`.
Keep passwords out of Git and make the certificate and spill directory available on every worker that can run the task.
With `verify-full`, the server certificate must match the hostname.
The example explicitly enables tombstones for consumers of compacted topics.

== Connector configuration

The Debezium column shows the defaults from the captured Debezium 3.6 configuration contract.
The Optimized connector column shows runtime defaults or values you must supply.
Unset means that no value is configured.
The `optimized.*` settings are specific to this connector.

The connector exposes the captured Debezium configuration contract through REST.
Some advertised defaults differ from the runtime defaults in `CandidateConfig` and `OptimizedSettings`.
Set operationally significant values explicitly and use the following tables to check supported settings.

|`database.initial.statements` — connection initialization SQL | Unset | Unset. Separate statements with `;` and escape a literal semicolon as `;;`.
|`database.sslmode` — TLS mode | `prefer` | `prefer`. Use `verify-full` in production when your PKI supports it.
|`database.sslrootcert` — trusted CA file | Unset | Unset. Supply a path available on the worker.
|`database.sslcert` — client certificate | Unset | Unset. Passed to JDBC.
|`database.sslkey` — client certificate key | Unset | Unset. Supply a path on the worker and keep the key out of Git.
|`database.sslpassword` — TLS key password | Unset | Unset. Treat it as a secret.
|`database.sslfactory` — TLS factory | Unset | Unset. Passed to JDBC.
|`database.tcpKeepAlive` — TCP keepalive | `true` | `true`
|`driver.*` — additional PostgreSQL JDBC properties | Additional JDBC options | Passed to JDBC with the prefix stripped. These can override shared settings. `connectTimeout` defaults to `5` seconds.

[cols="40%a,25%a,35%a",options="header"]
|===
|Parameter and purpose | Debezium | Optimized connector
|`heartbeat.interval.ms` — heartbeat event interval | `0` (disabled) | `1000` ms. Set `0` to disable heartbeats. The value must be non-negative.
|`heartbeat.topics.prefix` — prefix for heartbeat topics | `__debezium-heartbeat` | `__debezium-heartbeat` with the default naming strategy
|`heartbeat.action.query` — SQL executed for heartbeat activity in the database | Unset | Unset. Use an approved, idempotent query.
|`topic.naming.strategy` — topic naming strategy | `io.debezium.schema.SchemaTopicNamingStrategy` | Same default. A custom strategy requires an available SPI class.
|`signal.data.collection` — table for snapshot signals | Unset | Unset. Supply one exact `schema.table` name.
|`signal.enabled.channels` — signal channels | `source` | `source`. Accepts `source`, `kafka`, or both.
|`signal.poll.interval.ms` — signal polling interval | `5000` | `5000` (non-negative integer)
|`signal.kafka.topic` — Kafka signaling topic | Depends on Kafka signal channel configuration | `<topic.prefix>-signal` by default
|`signal.kafka.groupId` — Kafka signal consumer group | Separate Kafka signal channel setting | `kafka-signal`
|`signal.kafka.bootstrap.servers` — brokers for Kafka signaling | Kafka signal channel setting | Required when `kafka` is enabled
|`signal.kafka.poll.timeout.ms` — consumer poll timeout | Kafka signal channel setting | `100` (non-negative integer)
|`signal.consumer.*` — additional consumer properties | Kafka signal channel setting | Passed to the consumer with the prefix stripped. The channel sets its bootstrap servers, group, deserializers, and auto-commit policy.
|`incremental.snapshot.chunk.size` — incremental snapshot chunk size | `1024` | `1024` (positive integer)
|`read.only` — read-only mode for incremental snapshots | Depends on Debezium version | `false`
|===

The task emits heartbeats during polling. Snapshots, queued work, and in-flight batches can delay emission beyond the configured interval.
The default heartbeat topic is `__debezium-heartbeat.<topic.prefix>`.
Use `status.update.interval.ms` to configure replication status updates independently.

=== Performance and memory

[cols="40%a,25%a,35%a",options="header"]
|===
|Parameter and purpose | Debezium | Optimized connector
|`poll.interval.ms` — SourceTask polling interval | `500` | `100` (at least `1`)
|`max.batch.size` — maximum records per poll | `2048` | `8192`. Must be positive and no greater than `max.queue.size`.
|`max.queue.size` — record queue limit | `8192` | `32768` (positive integer)
|`optimized.execution.mode` — processing pipeline | Unavailable | `fast` only. `auto` and `debezium` are rejected.
|`optimized.processing.workers` — number of internal workers | Unavailable | `1` (range `1..64`)
|`optimized.processing.chunk.size` — internal processing chunk size | Unavailable | `512` (positive integer)
|`optimized.max.inflight.transactions` — transactions in flight | Unavailable | `16` (positive integer)
|`optimized.max.inflight.bytes` — transaction buffer memory threshold | Unavailable | `67108864` bytes (positive integer). Applies to transaction buffers.
|`optimized.transaction.spill.directory` — disk space for large transactions | Unavailable | `${java.io.tmpdir}/optimized-postgres-transactions`. Set an explicit working directory and monitor its free space.
|`optimized.raw.utf8.enabled` — accelerated UTF-8 processing | Unavailable | `false`. Test this option with your workload before enabling it.
|===

`max.batch.size` limits the records returned by one poll. `optimized.processing.chunk.size` sets the size of an internal processing chunk.

Start with explicit defaults and measure throughput, p95 latency, CPU, memory, lag, and spill size.
Change one setting per run.
When comparing with Debezium, keep Kafka Connect, the JVM, the data and event format, and the snapshot, heartbeat, and tombstone settings equivalent.
Measure the effect before increasing the worker count further.

== Limitations and upgrades

`FastPathSelector` accepts a defined set of properties. It rejects settings such as `max.queue.size.in.bytes`, `snapshot.max.threads`, `snapshot.fetch.size`, `snapshot.delay.ms`, `snapshot.isolation.mode`, `message.key.columns`, `slot.max.retries`, `slot.retry.delay.ms`, `lsn.flush.*`, `notification.*`, `openlineage.*`, `post.processors`, `publish.via.partition.root`, and `replica.identity.autoset.values`.
Use the settings listed in this guide when migrating a Debezium configuration.

`slot.stream.params` accepts `proto_version=1..4`. The default is `1`, or `3` when `two_phase=true` and no version is specified.
`two_phase=true` requires version `3` or later. `streaming=on` requires an explicit version of `2` or later.
`streaming` accepts `on` and `off`. Set the publication with `publication.name` and use unique keys in the stream parameters.
Validate two-phase transactions, failover, and distributed exactly-once with your environment.

Logical messages are disabled by default in the native pipeline.
To enable them, configure either `message.prefix.include.list` or `message.prefix.exclude.list` with regular expressions.
Test the event format and filters before deployment.

`transaction.boundary` accepts `poll` or `connector` and defaults to `poll`.
For exactly-once delivery, configure the distributed worker and Kafka broker and verify the selected transaction mode.

Before upgrading, back up the configuration, current plugin archive, and offsets as described in the xref:../upgrading.adoc[upgrade guide].
Stop capture while retaining the slot and install the same plugin version on every worker.
After resuming, check lag and sample insert, update, and delete events.
Stagger changes to the topic prefix, slot, converters, and event format.
Preserve the CDC position and restore the saved offsets when rolling back.

See also xref:../operations.adoc[Operations and troubleshooting] and xref:../upgrading.adoc[Upgrades and rollback].
